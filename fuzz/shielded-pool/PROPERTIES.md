# PROPERTIES

Discovered invariants for the SPP shielded pool. `SHOULD-HOLD` = expected to always
hold; `EXPLORATORY` = worth fuzzing but may be refined or dropped.

| ID | Property | Tag | Category | Status |
|----|----------|-----|----------|--------|
| P-0001 | NATIVE SOL SOLVENCY: the SOL interface account's lamport balance equals its opening balance, plus the sum of every amount credited by a successful `deposit`, minus the sum of every amount paid out by a successful withdrawal. The program never checks this relation itself — each deposit independently transfers lamports in and appends a UTXO crediting that amount — so a deposit that credits a UTXO for more than it moved (or moves less than it credits) leaves the pool insolvent against its own commitments with nothing on-chain objecting. The balance also carries a DONATION term, which is not a weakening but a correction: the SOL interface is system-owned, so anyone may transfer lamports into it for free and the pool cannot refuse. The original form asserted plain equality and claimed every lamport arrived through a settlement -- true only because nothing in the harness had ever donated, and it would have reported the first donation as insolvency. Accounting for donations rather than relaxing the bound to an inequality keeps it exact, so any lamport the harness cannot explain still fires; the direction that would be theft is P-0031. | SHOULD-HOLD | conservation | implemented |
| P-0002 | SPL SOLVENCY: the per-mint SPL interface token account's `amount` equals the sum of every amount credited by a successful SPL `deposit`. Kept separate from P-0001 rather than generalised, because the two rails move value by different mechanisms (system transfer vs token-program CPI) and are gated by different validation (`validate_sol_settlement` vs `validate_spl_settlement`); one combined property would pass whenever either rail happened to be consistent. | SHOULD-HOLD | conservation | implemented |
| P-0003 | STATE TREE MONOTONICITY: `UtxoTreeLayout.next_index` never decreases. Seven instructions append to the UTXO tree and none of them checks this, because in each one it plainly cannot happen; the property is about the seven together and about the paths that do not exist yet. A leaf index that rewinds reissues a committed UTXO's slot, so an inclusion proof against an older root can be replayed against a newer one. | SHOULD-HOLD | monotonicity | implemented |
| P-0004 | LEAF-COUNT INTEGRITY: `UtxoTreeLayout.next_index` equals the leaves `setup()` seeded plus the number of UTXOs every successful instruction appended. Strictly stronger than P-0003 and a different failure: monotonicity still holds if an instruction appends one UTXO and advances the counter by two (stranding an index no commitment occupies) or appends two and advances by one (overwriting a committed leaf on the next append). No handler is in a position to check it — `append_batch` advances the counter itself — so the identity the seven appending paths exist to maintain has no on-chain guard at all. | SHOULD-HOLD | conservation | implemented |
| P-0005 | NULLIFIER NON-REUSE: no nullifier is ever accepted twice, by any instruction, in any order. | P-0006 | WITHDRAWAL RECIPIENT BINDING: a successful `transact` withdrawal pays only the recipient its proof bound. | P-0016 | A SPLIT TRANSACT ROUTES THE NULLIFIER AND THE LEAF TO DIFFERENT TREES, AND TO THE RIGHT ONES: `transact` takes two tree accounts and they may differ.

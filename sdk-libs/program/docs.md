# Zolana program SDK

The Zolana program SDK defines zk program logic as Rust circuits that check private state changes and transfers and bind them to a zolana shielded-pool transaction.

The circuits are defined in a Rust crate alongside the Solana program.

The developer defines circuit public and private inputs with normal rust types.  
Macros derive the circuit equivalent types and client wasm bindings for state deserilization, witness generation and proving.

The zolana cli build command unifies the build of circuits, program and wasm for ts clients.

## Development of a Zk program

1. **Implement Solana Program with Circuit**
   1. Define state types, UTXOs with data, and Solana accounts.
   2. Define public and private inputs with Rust types.
   3. Implement the circuit’s checks, transfers, and transaction assembly.
   4. Implement the Solana instruction that verifies the proof and invokes SPP.
2. **Build Solana Program and Circuit**
   1. Run `zolana build-zk-program -p <crate>`.
   2. Export the circuits as R1CS.
   3. Generate or reuse proving and verifying keys and generate verifier modules.
   4. Build the wasm package for TypeScript clients.
   5. Build the Solana program.
3. **Client.**
   1. Decode state UTXOs.
   2. Prepare public and private inputs and the transaction context.
   3. Run the circuit in the client to construct the shielded transaction.
   4. Encrypt the outputs.
   5. Generate the circuit and shielded-pool proofs.
   6. Build the instruction.
   7. **Send Transaction**
      1. **Zk Solana Program:**
         1. Check the instruction’s accounts and public values.
         2. Check arbitrary other program logic.
         3. Verify the zk program proof.
         4. Invoke SPP, verifies spp proof, updates Merkle trees.

## Glossary


| #   | Term                | Definition                                                                                                                                                                      |
| --- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | ZK program          | A Solana program that verifies circuit proofs before invoking SPP.                                                                                                              |
| 2   | Circuit             | Rust code that defines the checks of a zk proof.                                                                                                                                |
| 3   | ZK proof            | Generated by the client and verified by the Solana program to check a private state transition.                                                                                 |
| 4   | Private inputs      | Circuit inputs supplied by the client and kept private from the Solana program.                                                                                                 |
| 5   | Public inputs       | Values set by the Solana program that tie the zk proof to verified state. They are hashed with the transaction hash using Poseidon to form the circuit’s single public input.   |
| 6   | ProofInputs         | The circuit’s input and intermediate values used to generate a zk proof.                                                                                                        |
| 7   | State UTXO          | A UTXO that holds private program data accessible in the circuit. The data struct must implement hashing. The UTXO’s data hash commits to that data.                            |
| 8   | SPP proof           | A zk proof that SPP verifies to check UTXO spends and transaction balances.                                                                                                     |
| 9   | SPP                 | The zolana shielded pool program that verifies transaction proofs and applies private transfers and UTXO state changes.                                                         |
| 10  | R1CS                | The circuit’s checks exported as equations for key generation and proving.                                                                                                      |
| 11  | Proving key         | Public data the client uses to generate zk proofs. Each circuit has its own proving key.                                                                                        |
| 12  | Verifying key       | Public data the Solana program uses to verify zk proofs generated with the corresponding proving key. Each circuit has its own proving key and verifying key pair.              |
| 13  | Wasm package        | WebAssembly code and TypeScript bindings for decoding state UTXOs, building transactions, and generating zk proofs.                                                             |
| 14  | Circuit types       | Generated equivalents of the Rust input types whose operations produce proof constraints instead of just computing values. The same circuit code can also run on client values. |
| 15  | Verifier module     | Generated Rust code containing a circuit’s verifying key and the function the Solana program calls to verify its zk proofs.                                                     |
| 16  | Transaction context | Settings the client passes to the circuit to choose the output tree and randomize output commitments.                                                                           |




## State

State is program data stored in UTXOs or Solana accounts.

State can be defined in a rust struct, should implement serialization as for a normal Solana account and a Poseidon hashing scheme to produce a data hash of the full state. This data hash is used to access the state in the circuit.

The data hash can be stored in a Solana account or the UTXO data hash field.

We recommend to store the actual data in a Solana account or the output utxo data field. If the Solana program logic does not enforce data availability the data can also be stored in a database.  The data needs to be sufficient to recompute the data hash. If the data is lost the UTXO and funds dependent on it are lost. 

### UTXO

A counter's state can be stored in a UTXO. `UtxoState` generates the state hashing, the `CounterCircuit` type, and a Borsh-backed `EncryptionCodec`. The UTXO's data hash commits to the full counter state. By default, its encrypted `utxo_data` contains the same complete Borsh representation used elsewhere.

```rust
#[derive(Clone, BorshSerialize, BorshDeserialize, UtxoState)]
pub struct Counter {
    pub owner: UtxoOwner,
    pub count: u64,
}
```

**Encryption payload**

`EncryptionCodec` controls the plaintext passed to encryption and reconstructs the state after decryption. It is separate from the state's normal `BorshSerialize` and `BorshDeserialize` implementations. The default codec preserves existing payload bytes and rejects malformed or trailing bytes when decoding. Custom Rust codecs also compile into WASM: generated state bindings use the codec and return the reconstructed full state to JavaScript.

For a smaller payload, add `#[utxo_state(custom_codec)]` and implement the trait manually. Omitted fields must be reconstructed using only the payload or constants fixed by the type. This example encrypts `count` and recomputes `doubled`; ordinary Borsh serialization still includes both fields:

```rust
use borsh::{BorshDeserialize, BorshSerialize};
use zolana_program::{circuit::UtxoState, EncryptionCodec};

#[derive(Clone, BorshSerialize, BorshDeserialize, UtxoState)]
#[utxo_state(custom_codec)]
pub struct CompactCounter {
    pub count: u64,
    pub doubled: u64,
}

#[derive(BorshSerialize, BorshDeserialize)]
struct CounterPayload {
    count: u64,
}

impl EncryptionCodec for CompactCounter {
    fn serialize_for_encryption(&self) -> std::io::Result<Vec<u8>> {
        borsh::to_vec(&CounterPayload { count: self.count })
    }

    fn deserialize_after_decryption(bytes: &[u8]) -> std::io::Result<Self> {
        let payload = CounterPayload::try_from_slice(bytes)?;
        let doubled = payload.count.checked_mul(2).ok_or_else(|| {
            std::io::Error::new(std::io::ErrorKind::InvalidData, "doubled count overflows")
        })?;
        Ok(Self { count: payload.count, doubled })
    }
}
```

Before accepting an outgoing payload, the SDK decodes it and checks that the reconstructed state's hash matches the original. For example, `CompactCounter { count: 3, doubled: 6 }` passes, while `{ count: 3, doubled: 7 }` fails with `CircuitError.StateRoundTripMismatch`. After decryption, the SDK verifies the reconstructed state against the UTXO commitment as well. These encoding checks run on the client and add no proof constraints.

Do not use `#[borsh(skip)]` to optimize the encryption payload: it changes ordinary Borsh serialization too, and the default `UtxoState` codec rejects directly skipped fields. Use a custom codec instead. Custom codecs can also be implemented for states without Borsh implementations. Their decoders must reject trailing bytes. If a custom payload format changes incompatibly, use an explicit version and retain the decoding needed for existing UTXOs; the SDK does not infer payload versions or fall back to Borsh.

**Manual implementation**

The Rust state and circuit traits generated by `UtxoState` can be implemented manually. Handwritten states also implement `EncryptionCodec`; there is no blanket implementation for Borsh types, so each state can choose its encryption representation.

Both implementations hash the discriminator, owner, and count in declaration order. With the corresponding features enabled, `UtxoState` also generates JSON serialization, TypeScript types, and the `counterDataUtxo` wasm binding.

This code replaces the `Counter` declaration above:

```rust
#[derive(Clone, BorshSerialize, BorshDeserialize)]
pub struct Counter {
    pub owner: UtxoOwner,
    pub count: u64,
}

impl Discriminator for Counter {
    // First eight bytes of SHA-256("account:Counter").
    const DISCRIMINATOR: [u8; 8] = [0xff, 0xb0, 0x04, 0xf5, 0xbc, 0xfd, 0x7c, 0x19];
}

impl DataHasher for Counter {
    fn hash(&self) -> Result<[u8; 32], HasherError> {
        let discriminator = u64::from_be_bytes(Self::DISCRIMINATOR).to_byte_array()?;
        let owner = self.owner.to_byte_array()?;
        let count = self.count.to_byte_array()?;
        Poseidon::hashv(&[&discriminator, &owner, &count])
    }
}

impl ToByteArray for Counter {
    fn to_byte_array(&self) -> Result<[u8; 32], HasherError> {
        DataHasher::hash(self)
    }
}

impl EncryptionCodec for Counter {
    fn serialize_for_encryption(&self) -> std::io::Result<Vec<u8>> {
        borsh::to_vec(self)
    }

    fn deserialize_after_decryption(bytes: &[u8]) -> std::io::Result<Self> {
        Self::try_from_slice(bytes)
    }
}
```

## Circuit

A circuit defines the logic of a zk proof. A circuit is compiled once to r1cs, from that a proving key is created with a trusted setup, a verifying key is derived from the proving key, the verifying key is used in the Solana program to verify the zk proof.

A circuit has public and private inputs: the client uses both to generate a zk proof, and the Solana program sets the public inputs to verify it without learning the private inputs.



### Example Increment Counter

```rust
// Circuit Definition
//
// A zk program circuit is defined by a Rust struct with two fields: private and public.
// ZkProgramCircuit generates the corresponding IncrementCircuit type, on which the circuit’s
// checks are implemented.
#[derive(Clone, ZkProgramCircuit)]
pub struct Increment {
    pub private: IncrementPrivateInputs,
    pub public: IncrementPublicInputs,
}

// Private inputs
//
// The client passes the counter UTXO and its Counter state as private inputs, together
// with the transaction context. The circuit checks the supplied state against the
// UTXO’s data hash. ProofInput generates the circuit equivalent of the input struct.
#[derive(Clone, ProofInput)]
pub struct IncrementPrivateInputs {
    pub tx_context: TxContext,
    pub counter: WalletUtxo,
    pub state: Counter,
}

// Public inputs
//
// The public input step specifies how much to increment the counter. The Solana program
// sets this value when verifying the proof. PublicInputs generates the circuit
// equivalent of the input struct and the public-input hashing.
#[derive(Clone, PublicInputs)]
pub struct IncrementPublicInputs {
    pub step: u64,
}

// Circuit Logic Definition
//
// Implement Circuit on IncrementCircuit to check the input state and construct a
// transaction that increments the counter by the public step.
impl Circuit for IncrementCircuit {
    type Output = CheckedTransaction;

    fn circuit(&self) -> Result<Self::Output, CircuitError> {
        let mut counter =
            DataUtxo::new_mut(&self.private.counter, &self.private.state)?;

        counter.count = counter
            .count
            .checked_add(&self.public.step, "the counter overflows")?;

        ConfidentialTransaction::new(&self.private.tx_context, &self.public)
            .with(counter)
            .check()
    }
}
```

### Circuit Types

SDK circuit types are available through `zolana_program::circuit`. The code blocks list documented public SDK methods and their interfaces.

1. **`TokenUtxos`**

   A token balance for one owner and asset, backed by zero or more input UTXOs. Also provides the shared [UtxoTrait methods](https://github.com/helius-labs/zk-tools/blob/jorrit/feat-zk-dsl/zk-dsl/spec.md#utxotrait-methods). `new_mut` requires at least one real input unless `with_optional(owner, asset)` is used. That builder allows all input slots to be dummies and supplies the owner and asset for the empty group. Real inputs must match the supplied owner and asset. Configure optional inputs before balance operations. The real-input requirement is checked during transaction registration.

```rust
impl TokenUtxos {
    // Initializes a zero token balance for the specified owner and asset.
    fn new_init(owner: &UtxoOwner, asset: &SolanaAddress) -> Self;

    // Spends matching inputs and produces change from the remaining balance.
    fn new_mut<const N: usize>(inputs: &[Utxo; N]) -> Result<Self, CircuitError>;

    // Allows zero real inputs, using the supplied owner and asset for the empty group.
    fn with_optional(self, owner: &UtxoOwner, asset: &SolanaAddress) -> Self;

    // Keeps a real token output when its balance is zero.
    fn with_zero_output(self) -> Self;

    // Requires a final balance of zero, produces no output, and rejects incoming transfers.
    fn close(self) -> Self;
}

impl UtxoTrait for TokenUtxos {
    // Returns the UTXO owner.
    fn owner(&self) -> UtxoOwner;

    // Returns the asset held by the UTXO.
    fn asset(&self) -> SolanaAddress;

    // Returns the balance as a checked 64-bit amount.
    fn amount(&self) -> Result<Uint<64>, CircuitError>;

    // Moves an amount to a same-asset destination and checks sufficient balance.
    fn transfer(&mut self, destination: &mut impl UtxoTrait, amount: &Uint<64>) -> Result<(), CircuitError>;

    // Moves the entire balance to a same-asset destination.
    fn transfer_all(&mut self, destination: &mut impl UtxoTrait) -> Result<(), CircuitError>;

    // Records a public deposit from the source and credits the balance.
    fn deposit(&mut self, amount: &Uint<64>, source: &SolanaAddress) -> Result<(), CircuitError>;

    // Records a public withdrawal to the destination and checks sufficient balance.
    fn withdraw(&mut self, amount: &Uint<64>, destination: &SolanaAddress) -> Result<(), CircuitError>;

    // Records a withdrawal of the entire balance and returns the amount.
    fn withdraw_all(&mut self, destination: &SolanaAddress) -> Result<Uint<64>, CircuitError>;
}
```

2. **`DataUtxo<S>`**

   A state UTXO with data of type `S` and a token balance. State fields and methods are accessible through `Deref` and `DerefMut`. Also provides the shared [UtxoTrait methods](https://github.com/helius-labs/zk-tools/blob/jorrit/feat-zk-dsl/zk-dsl/spec.md#utxotrait-methods). The `*_with_hash` methods apply to `DataUtxo<CircuitVar>` and use an application-provided state hash.

```rust
impl<S> DataUtxo<S> {
    // Initializes default state with a zero SOL balance.
    fn new_init(owner: &UtxoOwner) -> Self where S: Default;

    // Checks the state commitment and spends the input to produce updated state.
    fn new_mut(input: &Utxo, state: &S) -> Result<Self, CircuitError> where S: DataHash + Clone;

    // Sets the asset of a newly initialized, unused UTXO.
    fn with_asset(self, asset: &SolanaAddress) -> Result<Self, CircuitError>;

    // Requires a final balance of zero, produces no output, and rejects incoming transfers.
    fn close(self) -> Self;
}

impl DataUtxo<CircuitVar> {
    // Initializes state with an application-provided hash and a zero SOL balance.
    fn new_init_with_hash(owner: &UtxoOwner, data_hash: &CircuitVar) -> Self;

    // Checks the application-provided hash and spends the input to produce updated state.
    fn new_mut_with_hash(input: &Utxo, data_hash: &CircuitVar) -> Result<Self, CircuitError>;
}
```

3. **`UniqueDataUtxo<S>`**

   A state UTXO with a unique address derived from its owner and seed. State fields and methods are accessible through `Deref` and `DerefMut`. Also provides the shared [UtxoTrait methods](https://github.com/helius-labs/zk-tools/blob/jorrit/feat-zk-dsl/zk-dsl/spec.md#utxotrait-methods). `new_init` derives the address and prepares its reservation; `.with(state)` registers the reservation together with the state output.

```rust
impl<S> UniqueDataUtxo<S> {
    // Reserves the owner-and-seed address and initializes default state with a zero SOL
    // balance.
    fn new_init(owner: &UtxoOwner, seed: &CircuitVar) -> Result<Self, CircuitError> where S: Default;

    // Checks the address and state commitment and spends the input to produce updated state.
    fn new_mut(input: &Utxo, address: &CircuitVar, state: &S) -> Result<Self, CircuitError> where S: DataHash + Clone;

    // Sets the asset of a newly initialized, unused UTXO.
    fn with_asset(self, asset: &SolanaAddress) -> Result<Self, CircuitError>;

    // Returns the state UTXO’s unique address.
    fn address(&self) -> CircuitVar;

    // Requires a final balance of zero, leaves an empty UTXO with address, and rejects incoming transfers.
    fn close(self) -> Self;

    // Requires a final balance of zero, produces no output, and rejects incoming transfers.
    fn burn(self) -> Self;
}
```

4. **`NewAddress`**

   An address reservation independent of a state output. `.with(address)` registers the reservation. `UniqueDataUtxo::new_init` includes its own reservation.

```rust
impl NewAddress {
    // Derives the owner-and-seed address and prepares its reservation.
    fn new(owner: &UtxoOwner, seed: &CircuitVar) -> Result<Self, CircuitError>;

    // Returns the derived address.
    fn address(&self) -> CircuitVar;
}
```

5. **`ConfidentialTransaction<'a, P>`**

   Builds a transaction from registered UTXOs, address reservations, public transfers, and public inputs. Requires `P: PublicInputs`. Padding is compact by default; `with_dummy_padding()` preserves dummy input slots and publishes dummy padding. `.with(item)` delegates registration to `TransactionItem`; registration errors are returned by `check()`.

     `TransactionItem` is implemented for `TokenUtxos`, `DataUtxo<S: UtxoData>`, `DataUtxo<CircuitVar>`, `UniqueDataUtxo<S: UtxoData>`, and `NewAddress`. State UTXOs include their serialized state; `DataUtxo<CircuitVar>` registers a raw state hash whose plaintext is transported separately.

```rust
trait TransactionItem {
    // Registers the item's inputs, outputs, public transfers, and address reservations.
    fn register<P: PublicInputs>(self, transaction: &mut ConfidentialTransaction<'_, P>);
}

impl<'a, P: PublicInputs> ConfidentialTransaction<'a, P> {
    // Starts a transaction with its context and public inputs.
    fn new(tx_context: &'a TxContext, public: &'a P) -> Self;

    // Preserves dummy input slots and publishes dummy padding.
    fn with_dummy_padding(self) -> Self;

    // Registers a UTXO or address reservation.
    fn with(self, item: impl TransactionItem) -> Self;

    // Checks registered transfers and outputs, derives output commitments, and computes the
    // transaction and public hashes.
    fn check(self) -> Result<CheckedTransaction, CircuitError>;
}
```

## **Solana Program with Circuit**

- it is just a solana program that uses zk circuits to verify private checks
- The solana program can have instructions that do anything and are not related to zk at all.
- For the instructions that use a zk circuit and UTXOs such as an escrow, they invoke the SPP to execute the state transition.
- To access state in a zk circuit it needs to be hashed. State can be in UTXOs as hashed data as private input or in a Solana account public input.

The handler reads `IncrementArgs` followed by the SPP transaction payload, verifies the circuit proof, and invokes SPP with the program’s counter PDA as the UTXO owner.

```rust
#[derive(SchemaRead, SchemaWrite)]
pub struct IncrementArgs {
    pub proof: CompressedProof,
    pub step: u64,
}

pub fn process_increment_ix(accounts: &mut [AccountView], data: &[u8]) -> ProgramResult {
    // Decode the arguments and the SPP payload that follows them.
    let mut transact_data = data;
    let args: IncrementArgs = wincode::deserialize_from(&mut transact_data)
        .map_err(|_| ProgramError::InvalidInstructionData)?;
    let tx = TransactIxDataRef::from_bytes(transact_data)
        .map_err(|_| ProgramError::InvalidInstructionData)?;

    // Verify the proof with the public step and the transaction being executed.
    ProgramVerifier {
        circuit: increment::Verifier {
            proof: &args.proof,
            public_inputs: increment::PublicInputs { step: args.step },
        },
        private_tx_hash: tx.private_tx_hash,
        deposits_and_withdrawals: &[],
    }
    .verify()?;

    // Validate the SPP accounts and sign for the counter’s PDA owner.
    let (authority, bump) =
        Address::find_program_address(&[COUNTER_AUTHORITY_SEED], &crate::ID);
    let bump = [bump];
    let seeds = [Seed::from(COUNTER_AUTHORITY_SEED), Seed::from(&bump)];
    SppTransactAccounts::new(accounts, &[&authority])?
        .invoke::<16>(transact_data, &[Signer::from(&seeds)])
}
```

## Build

The Zolana CLI builds the circuits, verifier modules, client wasm package, and Solana program.

```sh
zolana build-zk-program -p <crate>
```

1. **Circuits:** discovers structs deriving `ZkProgramCircuit` and exports each circuit to `target/zk/<crate>/<circuit>.r1cs`.
2. **Keys:** generates proving and verifying keys when missing or when the circuit’s R1CS changes. Otherwise, reuses existing keys.
3. **Verifiers:** generates Rust modules in `src/verifier/` containing each circuit’s public inputs, verifier, and verifying key.
4. **Client wasm:** builds the TypeScript bindings for state decoding, transaction construction, and proving.
5. **Solana program:** runs `cargo build-sbf` with the generated verifier modules.

### Crate Configuration

Declare the build features in `Cargo.toml`:

```toml
[lib]
crate-type = ["cdylib", "lib"]

[features]
circuits = ["zolana-program/client"]
r1cs-export = ["zolana-program/r1cs-export"]
wasm = ["zolana-program/wasm"]
insecure-test-setup = []

[dependencies]
zolana-program = { workspace = true, features = ["cpi", "verifier"] }
```

In `lib.rs`, enable circuit definitions for circuit and wasm builds. Exclude generated verifiers and their callers during R1CS export so the first build works before verifier files exist. Apply the same exclusion to the program entrypoint.

```rust
#[cfg(any(feature = "circuits", feature = "wasm"))]
pub mod circuits;

#[cfg(not(feature = "r1cs-export"))]
pub mod verifier;

#[cfg(not(feature = "r1cs-export"))]
pub mod instructions;
```

### Test Build

Use `--test` to generate reproducible keys using a fixed test seed. Keys are generated when missing or when the circuit’s R1CS changes and reused otherwise.

```sh
zolana build-zk-program -p <crate> --test
```

### Check Binary

Use `zolana vks check` to inspect the verifying-key setup markers in a local binary or deployed program. The command reports the keys found, whether any use a test setup, and an overall pass or fail result with reasons. If no markers are found, it reports that the setup is unknown. Failed checks return a nonzero exit code for CI.

```sh
# Check a local program binary before deployment.
zolana vks check --so target/deploy/<program>.so

# Check the deployed program.
zolana vks check --program-id <program-id> --rpc-url <rpc-url>
```

Each verifying key’s binary marker includes the SHA-256 hash of its corresponding proving key, using `groth16-solana`’s setup metadata. Pass the proving-key checksum manifest with `--expect` to compare its hashes with those embedded in the binary. The command reports missing or mismatched hashes; it reads the manifest rather than hashing the proving-key files itself.

```sh
zolana vks check --program-id <program-id> --rpc-url <rpc-url> \
  --expect target/zk/<crate>/<circuit>.pk.sha256
```

## Client

The client uses the generated wasm package to decode state, construct transactions, and generate proofs for the Solana program.

1. Fetch and decode the counter UTXO.
2. Set the public and private inputs.
3. Run the circuit to construct the transaction.
4. Encrypt outputs and generate the circuit and SPP proofs.
5. Build and submit the Solana instruction.

### TypeScript

The example assumes initialized wasm, a fetched and decrypted `counterWalletUtxo`, and the matching proving key and trusted checksum. `shieldedPda` provides the owner identity and nullifier key for the program-owned UTXO. Proof generation accepts an array of owner keypairs and matches inputs by signing identity, independently of keypair order. `incrementInstruction` and `sendAndConfirm` are application helpers for constructing and submitting the instruction.

Bind the generated wasm function once to a trusted asset registry. The wrapper validates each result against a snapshot of that registry and retains mint addresses and asset IDs together, so encryption needs no registry lookup. Bind again after registering additional assets.

```ts
import { ShieldedPda } from "@heliuslabs/zolana/keypair";
import { ProgramOwner, bindProgramTransaction } from "@heliuslabs/zolana/transaction";

const incrementTransaction = bindProgramTransaction(wasm.incrementTransaction, { assets });

const counter = wasm.counterDataUtxo(counterWalletUtxo);
const step = 1n;

// Run the circuit to prepare its proof inputs and the SPP transaction.
const { proofInputs: circuitProofInputs, transaction: sppTransaction } =
  await incrementTransaction(
    {
      private: {
        txContext: {
          blindingSeed: randomBlinding(),
          outputTreeId: client.treeId,
        },
        counter: counter.utxo,
        state: counter.data,
      },
      public: { step },
    },
    sender.shieldedAddress().toBytes(),
    payer.address,
  );

const prover = wasm.IncrementProver.fromKey(provingKey, expectedSha256);

const circuitProof = prover.prove(circuitProofInputs);

// Encrypt the outputs and generate the SPP proof.
const sppProofInputs = sppTransaction.encryptWithKeys(sender);
const shieldedPda = ShieldedPda.withViewingKey(
  authority.pda,
  ProgramOwner.nullifierKey(),
  sender.viewingKey(),
);
const transact = await client
  .proveTransact(sppProofInputs, [shieldedPda])
  .finally(() => shieldedPda.destroy());

const instruction = await incrementInstruction({
  programId,
  client,
  payer,
  authority,
  proof: circuitProof.compressedProof,
  step,
  transact,
});
await sendAndConfirm([instruction]);

```

### Rust

The Rust example uses the same fetched UTXO and loaded key bytes. `IncrementInstruction` and `send_and_confirm` are application helpers, matching the TypeScript helpers. The finalized transaction is already typed, so Rust can encrypt its outputs directly. Proof generation accepts a slice of `ShieldedKeypairTrait` implementations and matches inputs by signing identity, independently of keypair order.

```rust
let counter = zolana_program::DataUtxo::<Counter>::try_from(counter_wallet_utxo)?;
let step = 1;

let increment = Increment {
    private: IncrementPrivateInputs {
        tx_context: TxContext::new().with_output_tree_id(Some(tree_id)),
        counter: counter.utxo,
        state: counter.data,
    },
    public: IncrementPublicInputs { step },
};

// Run the circuit to prepare its proof inputs and the SPP transaction.
let ProgramTransaction {
    finalized,
    proof_inputs: circuit_proof_inputs,
    ..
} = increment.create_program_transaction(&sender.shielded_address()?, payer.pubkey())?;

let keys = Groth16Keys::from_bytes_checked(&proving_key, &expected_sha256)?;
let prover = Groth16Prover::<Increment>::new(keys)?;
let circuit_proof = prover.prove_inputs(&circuit_proof_inputs)?.compressed()?;

// Encrypt the outputs and generate the SPP proof.
let spp_proof_inputs = finalized.encrypt_with_keys(&sender)?;
let shielded_pda = ShieldedPda::with_viewing_key(
    *authority.pda(),
    ProgramOwner::nullifier_key(),
    sender.viewing_key.clone(),
);
let keypairs: &[&dyn ShieldedKeypairTrait] = &[&shielded_pda];
let transact = client.prove_transact(spp_proof_inputs, None, keypairs)?;

let instruction = IncrementInstruction {
    program_id,
    payer: payer.pubkey(),
    authority,
    tree,
    proof: circuit_proof,
    step,
    transact,
}
.instruction()?;
send_and_confirm(&client, &payer, &[instruction])?;
```

## Limitations

### Zk Circuits

1. **Fixed shape:** array lengths and loop bounds must be known when building the circuit. Variable-length collections need a maximum length. Dummys or compact padding can be used to alliviate this for token utxos.
2. **Conditional logic:** private values cannot control ordinary Rust branches. Use circuit conditions and selection to express conditional checks.
3. **Arithmetic:** field operations wrap around the field modulus. Use checked integer types when overflow or value ranges matter.
4. **Trusted setup:** each circuit requires a trusted setup. A single-party setup can fit an upgradeable program’s trust model when the setup operator is also the trusted upgrade authority. Setup secrets must be discarded; fixed-seed test setups are for testing only.
5. **Data hash privacy:** a state UTXO’s data hash is private by default and protected by the UTXO commitment’s blinding. If the data hash is published, include private random blinding in the hash to keep the underlying data private.

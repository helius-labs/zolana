# Key certification: K1 through K5

Suites K1 to K5 of [proof-and-key-parity.md](../proof-and-key-parity.md), run to
that document's `### Definition of parity`: material generated by the real Rust
implementation, committed, and replayed in TypeScript, with control edits to
show each suite can detect a divergence.

## Bottom line

**All five are certified.** Public-key encoding, P256 signing, Ed25519 signing,
nullifier derivation, and the viewing-key family agree with Rust on every input
in the corpus, byte for byte, including the adversarial ones.

**One divergence, in K2, at one input class.** For a P256 prehash at or above the
group order `n`, the two implementations produce different (both valid)
signatures, because the Rust `ecdsa` crate seeds the RFC 6979 nonce with the
unreduced digest and `@noble/curves` reduces it first. See
[The P256 nonce divergence](#the-p256-nonce-divergence). This needs a Rust-side
decision; TypeScript is the RFC-conformant side and was not changed to match.

Nothing was stopped for work in flight. The suites depend on `@zolana/keypair`
and on `@zolana/hasher`'s compiled Poseidon, neither of which moved under them;
the branch was merged with `origin/ts-sdk-port` at `d0e86036` (which carries
`feat(keypair)!: make ViewingKeyLike synchronous`) and everything below was
re-run against that.

## The evidence chain

Four artefacts, each of which fails independently:

| Artefact | What it is |
| --- | --- |
| `sdk-libs/keypair/tests/key_certification_vectors.rs` | Rust generator. Every disposition is **taken from the crate**, never asserted, so a behaviour change breaks it before it can be read as agreement. |
| `sdk-libs/ts/vectors/key-certification-v1.json` | The committed corpus, 119 KB, produced by the above. |
| `sdk-libs/ts/keypair/test/vectors/key-certification-k{1..5}-*.test.ts` | 50 tests replaying the corpus through the TypeScript SDK. |
| `sdk-libs/ts/vectors/key-certification-typescript-v1.json` + `sdk-libs/keypair/tests/key_certification_reverse.rs` | The reverse direction: TypeScript produces, Rust verifies. |

The reverse corpus is the part a replay cannot give you. A replay shows
TypeScript reproduces bytes Rust already wrote; it says nothing about whether
Rust accepts what TypeScript writes. The TypeScript test pins the corpus against
its own regeneration (`UPDATE_KEY_CERTIFICATION_VECTORS=1`), and the Rust test
both **verifies** each signature and **re-signs** it, since verification alone
would pass for any valid signature and only re-signing pins the deterministic
bytes.

Regenerate with:

```bash
UPDATE_KEY_CERTIFICATION_VECTORS=1 cargo test -p zolana-keypair --test key_certification_vectors
cd sdk-libs/ts/keypair && UPDATE_KEY_CERTIFICATION_VECTORS=1 npm run test:vectors
cargo test -p zolana-keypair --test key_certification_reverse   # must still pass
```

A regeneration the other language rejects is a divergence, not a refresh.

## K1: public-key encoding and parsing

Certified. 11 tests against 526 recorded dispositions.

| Corpus section | Cases | What it separates |
| --- | --- | --- |
| `p256PrefixSweep`, `ed25519PrefixSweep` | 256 each | Every one of the 256 tag bytes over a valid body of each rail. Only `0x00` and `0x01` parse; the other 254 must fail with `InvalidSignatureType`, not with a length or point error. |
| `p256Points` | 11 | x at 0, at `p − 1`, at `p`, above `p`, all-ones; both parity bytes; a point off the curve; a compressed prefix of `0x04`; the all-zero body. |
| `ed25519Padding` | 3 | The 34th byte must be zero. A port that ignores it accepts 255 spellings of the same key. |
| lengths | 0 to 40 | Both valid widths (34 tagged, 33 raw P256) accepted, every other width refused. |

Also certified: the zero sentinel is the dummy owner and not a parseable key
(`isZero()` true, `fromBytes` refuses it on the P256 rail); equality compares all
34 tagged bytes across rails and parities; `toBytes()` returns an owned copy
rather than a view into key state.

## K2: P256 signing and verification

Certified, with the divergence below. 10 tests.

| Corpus section | Cases | What it separates |
| --- | --- | --- |
| `scalars` | 6 | Secret at 0, 1, `n − 1`, `n`, `n + 1`, all-ones. The two ends of the group are the classic off-by-one in a range check. |
| `digestSweep` | 16 | Deterministic RFC 6979 signatures reproduced byte for byte, including the ones that land high-`s`. |
| `signatureCases` | 14 | `r` or `s` at zero, at `n`, above `n`; the negated-`s` twin; single-bit mutations; all-zero and all-ones. |
| `prehashLengths` | 5 | P256 signing takes a 32-byte prehash and nothing else. |
| `digestBoundaries` | 6 | Prehash at 0, 1, `n − 1`, `n`, `n + 1`, all-ones. |

**G2-1 is certified, not re-decided.** The ruling accepts high-`s`, so the suite
checks that a high-`s` signature the deployed circuit accepts verifies on both
sides, and that neither side normalizes into the lower half. A port that turned
`lowS` back on would produce different bytes for exactly those cases, which is
the second control edit below.

### The P256 nonce divergence

For a prehash `z >= n` the two signers disagree byte for byte:

- **TypeScript** follows RFC 6979 §2.3.4: `bits2octets(h1) = int2octets(bits2int(h1) mod n)`, so the HMAC seed is the reduced digest. `sign(z) == sign(z mod n)`.
- **Rust** (`ecdsa` 0.16.9, `hazmat::try_sign_prehashed_rfc6979`) passes the output of `bits2field` straight to `rfc6979::generate_k`. `bits2field` left-aligns or truncates but does not reduce, so the seed is the raw digest. `sign(z) != sign(z mod n)`.

That is a deviation on the Rust side, and from `rfc6979`'s own documented
contract, which says `h` "must be reduced modulo `n` in advance".

What it costs and does not cost:

- Both signatures are **valid**, and each language **verifies the other's**; the suite asserts this rather than assuming it. No authorization consequence.
- What is lost is that one key and one prehash stop naming one signature: a Rust-recorded fixture is not reproducible in TypeScript, and a wallet that re-signs the same spend in the other language produces different bytes.
- Reachability is small but not zero. The prehash is a SHA-256 digest, so `z >= n` has probability ≈ 2⁻³², and an adversary who wants to hit it can grind about 2³² transactions. The payoff is producing two different valid signatures over one spend, which the nullifier already prevents from becoming a double spend.

The suite **pins the divergence from both sides** rather than hiding it: it
asserts that Rust's recorded `matchesReducedDigestSignature` is `false`, that
TypeScript's is `true`, that the two signature bytes differ, and that each side
still verifies the other. It cannot change silently in either direction.

**Needs a Rust change, or an explicit ruling.** The options are to reduce the
prehash before RFC 6979 in `sdk-libs/keypair` (restores byte determinism, changes
Rust's own signature bytes for `z >= n`, which nothing yet depends on), to upgrade
`ecdsa` if a later release fixes the seed, or to rule the input class out of
scope and keep the pin. Not resolved here: it is a Rust-side signature-bytes
change and this port does not modify Rust behaviour. Light Protocol does not
address it, having no P256 rail of its own.

## K3: Ed25519 signing and verification

Certified. 8 tests.

Signatures reproduced byte for byte over an empty message, a single byte, a
32-byte digest, and 1000 bytes. Acceptance replayed over 10 malleated cases.

**G2-2 is certified, not re-decided.** The ruling is that acceptance mirrors the
Solana runtime, so the load-bearing cases are the ones where `verify_strict` and
the permissive check disagree:

| Case | Decision | Why it is the hinge |
| --- | --- | --- |
| `smallOrderR` | reject | `R` is the identity and `s = k·x mod L`, so the cofactored equation accepts it. Only strict verification refuses. |
| `nonCanonicalR` | reject | `y = p + 3` decodes to a full-order point, so it survives parsing and only the byte comparison against `R` refuses it. |
| `sAtOrder`, `sPlusOrder` | reject | `s` at and above `L`; a port that reduces instead of refusing accepts a second signature for one message. |

Rust's `SigningKey::verify` derives the verifying key from the secret, so a
caller cannot present a small-order or non-canonically encoded **public** key.
The suite asserts TypeScript does not widen that surface, because a
public-key-taking verifier on one side only would be a divergence in the input
domain even where every shared input agrees.

## K4: nullifier derivation and binding

Certified. 8 tests. Runs end to end through `@zolana/hasher`'s compiled
Poseidon (consumed, not touched, per the standing ruling).

- The 31-byte secret and its Poseidon public key match from both `fromSigningKey` and `fromSigningSecret`.
- Nullifiers match over an all-zero blinding, an all-ones blinding, and a zero UTXO hash.
- **The BN254 boundary**: a UTXO hash at `modulus − 1` derives, and at `modulus`, `modulus + 1`, and all-ones both sides refuse. An input above the field is not a different nullifier, it is no nullifier.
- **Binding**: the nullifier public key enters the owner hash, so swapping the nullifier key alone moves the owner hash. This is what makes a UTXO spendable only by the holder of the nullifier secret, and it is asserted against the Rust value for both keys.
- Same inputs repeat; any change to UTXO hash, blinding, or key moves the result.

## K5: viewing and transaction-viewing keys

Certified. 13 tests.

- **`P_const` is derived, not trusted.** The suite runs RFC 9380 `P256_XMD:SHA-256_SSWU_RO_` over the empty message with the committed DST and checks the result equals `P_CONST_SEC1` and the Rust-recorded bytes. A wrong constant would give a wallet a view root nobody else derives, and reading the committed bytes back would never show it.
- ECDH against a counterparty, a stranger, and `P_const` itself, which is the private view root's input.
- **All five tag families** over counters `0, 1, 2, 255, 256, 2³² − 1, 2⁶³, 2⁶⁴ − 1`: sender, recipient-request, merge, send-shared, recipient-shared, plus `recipientBootstrapViewTag`. Every tag byte-identical, every tag a 32-byte field element with a zero leading byte, all five domains distinct at the same counter, and counters outside u64 refused.
- **Shared tags agree from either end**: the sender's `sendSharedViewTag` equals the recipient's `recipientSharedViewTag`, derived independently in TypeScript, not merely equal to a recorded Rust boolean.
- **Epoch rotation**: `fromSeed` at accounts `0, 1, 2, 7, 65536, 2³² − 1`, each with a distinct secret, public key, and tag.
- **The scalar reduction**, which is where a port quietly differs: 24 seed and account combinations pin that the 48-byte HKDF output is reduced modulo the group order rather than truncated.
- **Transaction viewing keys** over four first-nullifiers including zero, all-ones, and `bn254 modulus − 1`; repeats for the same nullifier, differs from the base key.

Per ruling K11 every derivation here is synchronous, and the suite exercises
the concrete `ViewingKey` rather than an interface an out-of-process backend
could satisfy.

## Control edits

Eight, applied with `tools/control-edit.mjs`, each restored immediately. All
eight were caught, and each fails the tests that should fail rather than
everything:

| # | Edit | Suite | Result |
| --- | --- | --- | --- |
| 1 | Drop the Ed25519 padding check in `public-key.ts` | K1 | caught, 2 of 11 |
| 2 | Skip P256 point validation in `ShieldedPublicKey.fromBytes` | K1 | caught, 3 of 11 |
| 3 | `lowS: false` to `lowS: true` in `SigningKey.sign` | K2 | caught, 2 of 10 |
| 4 | Drop the small-order check in `verifyEd25519Strict` | K3 | caught, 1 of 8 |
| 5 | Swap the blinding and secret Poseidon inputs in `nullifier` | K4 | caught, 1 of 8 |
| 6 | Truncate the HKDF output instead of reducing it in `scalarFromOkm` | K5 | caught, 3 of 13 |
| 7 | Write the view tag at offset 0 instead of 1 | K5 | caught, 3 of 13 |
| 8 | Edit 3 again, against the reverse corpus | reverse | caught, corpus no longer matches |

Edit 5 is the one that matters most for K4: swapping two Poseidon inputs
preserves every width, every type, and every error path, and a suite that only
checked "a nullifier came back" would pass it.

## Not certified, and why

- **Small-order and non-canonically encoded public keys.** Neither language exposes a verification path taking a caller-supplied public key, so there is no shared input to compare. Asserted as a shape claim instead: TypeScript exposes no such path either.
- **The zero-scalar branch** in `scalarFromOkm` and its Rust counterpart. Both define the error; reaching it needs HKDF to land on a multiple of the group order. Recorded as `zeroScalarReachable: false` rather than tested.
- **Poseidon itself.** K4 depends on it and consumes `@zolana/hasher`; its parity is [poseidon-parity.md](poseidon-parity.md), not this work.
- **K6 to K10 and P1 to P5.** Out of scope for this dispatch.

## T25: TypeScript was stricter than Rust

Rust's `ConfidentialTransfer::new` stores the owner, inputs, and payer hash and
returns (`sdk-libs/transaction/src/instructions/transact/transfer.rs:89-98`).
TypeScript refused three inputs at construction: an empty list
(`TRANSACTION_NO_INPUTS`), a dummy (`TRANSACTION_DUMMY_INPUT_NOT_ALLOWED`), and
an input owned by anyone but the transfer owner
(`TRANSACTION_INPUT_OWNER_MISMATCH`).

The empty-input case was not an early refusal of the same later error. Rust's
own test at `transfer.rs:597-602` builds
`ConfidentialTransfer::new(owner, Vec::new(), Address::default())` and asserts
that a crossed asset and withdrawal target returns `WithdrawalAssetMismatch`.
TypeScript never reached `withdraw`, so the two languages named different
errors for one input. That test exists and says what the reconciler claimed.

The owner had already ruled the same class of question for T23: remove the
extra TypeScript checks and match Rust exactly, even where TypeScript was
safer. The three constructor refusals are deleted. `TRANSACTION_NO_INPUTS`
still fires from `prepare` when the list is empty, which is where Rust's
`first_nullifier` path reaches `NoInputs`.

Removing the owner check unblocked the wallet rail cases the constructor had
been intercepting. `SppProofInputs.applyP256Signature` still refused when no
input was P256-owned, which is not what Rust's `sign_p256` does: that path
checks the keypair's curve and stores the signature. The input-ownership and
`TRANSACTION_SIGNATURE_OWNER_MISMATCH` checks are deleted there too, so a P256
authority spending ed25519 notes builds the same way Rust does. Wallet rail
vectors that previously pinned the TypeScript-only refusal now replay Rust's
outcomes.

Pinned in `transaction/test/transfer.test.ts`: empty inputs construct and
`withdraw` raises `TRANSACTION_WITHDRAWAL_ASSET_MISMATCH`; a dummy input and a
foreign-owned input both construct without throwing.

## A01: quoting was laundering capped fields

`quoteUnsafeIntegers` existed so Photon responses that emit bare numbers past
`2^53` survive `JSON.parse` with their digits intact. That is Light's
`wrapBigNumbersAsStrings` answer, and deleting it would break the seven
unbounded fields. The defect was that it quoted every unsafe literal, including
those on capped fields.

The owner's ruling is per field. `slot`, `block_time`, `root_seq`, `seq`, and
`start_seq` accept a decimal string after the rewrite. Every other integer is
number-only and must refuse an unsafe value as a number. Quoting a
`leaf_index` past `2^53` turned that refusal into a type error for a string,
so the ruled precision-loss path could not fire when measured through
`ZolanaIndexer`.

The fix keeps the scanner's string-escape and position handling, and quotes
only when the preceding JSON key is one of those five names. An unsafe
`root_seq` is still quoted and still decodes exactly. An unsafe `leaf_index`
is left as a JSON number, `JSON.parse` hands the decoder a non-safe integer,
and `wireInteger` refuses it.

That is the approach that holds: the transport rewrite is a reader's survival
tool for the fields whose domain can exceed `2^53`, not a global integer
policy. Light applies the same split per field in its decoder; the port had
already done that half and was undoing it one layer up.

Pinned end to end in `client/test/indexer-client.test.ts` through
`ZolanaIndexer.getMerkleProofs`, not through the decoder in isolation: an
unsafe `leaf_index` raises `CLIENT_INVALID_RPC_RESPONSE` at
`$.proofs[0].leaf_index`, and an unsafe `root_seq` still returns the exact
`bigint`. The transport suite pins the same capped-field refusal at the API
layer with the schema code `INDEXER_SCHEMA_INVALID_INTEGER`.

C04's integer-domain residue was this A01 override. With the override gone, the
ruled refusal is reachable through the shipped stack, and the decoder field
split the reconciler already verified stands. The `api()` /
`with_http_trace` dispositions recorded on that row are unchanged.

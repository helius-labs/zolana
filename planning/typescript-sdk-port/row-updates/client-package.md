# `@zolana/client` parity: RPC and transport layer

Covers `C01`, `C02`, `C04`, `C05`, `C21`, `C22`, the non-prover half of the
package. The prover subtree (`C06` through `C20`) was worked in parallel and
reports separately.

Every claim below names the test that demonstrates it. Where a fix was made, the
entry records that the test was run against the pre-fix code and failed; a test
that passes both ways is not evidence and is marked as such.

## Divergences found and closed

### 1. Account order inside a privilege class (`C21`)

`compileLegacyTransaction` ordered the accounts inside each privilege class by
first appearance. `build_unsigned_solana_transaction` calls
`solana_message::Message::new`, whose `CompiledKeys` holds a `BTreeMap` keyed by
address, so each class comes out sorted ascending by the 32 raw bytes.

**Input that exposes it.** A SOL withdrawal. Its writable non-signers are the
tree (`[6; 32]`), the SOL interface, and the recipient (`[3; 32]`), which appear
in the instruction in an order that is not their byte order. The frozen legacy
message vectors could not have caught this: they only cover `withdrawal: None`,
where every class holds at most two accounts that already happen to be ascending.

**Evidence.** `sdk-libs/client/src/client.rs::legacy_message_account_order_oracle`
emits the header, account keys, and compiled index arrays that `Message::new`
produces, into `sdk-libs/ts/client/test/oracles/legacy-message-order-v1.json`.
`sdk-libs/ts/client/test/vectors/legacy-message-order.test.ts` compiles the same
withdrawal and compares. Reverting the sort to the old tiebreaker fails it.

**Follow-on.** `merge.test.ts` asserted two full message byte strings against
hand-written account arrays in first-appearance order, so the fix broke them
correctly. They now read
`sdk-libs/ts/client/test/oracles/merge-message-order-v1.json`, generated by
`client.rs::merge_message_account_order_oracle` over the instruction list
`sdk-libs/wallet/src/actions/submit.rs` sends, for both `merge_transact` and
`merge_zone`.

### 2. Confirmation refused records Rust confirms (`C21`)

This is the "TypeScript rejects input Rust accepts" pattern the brief warns
about, and it is the highest-impact one found in this half.

`confirmPrivateTransaction` required every requested output view tag to reappear
in the indexed record's `outputSlots` or `messages`.
`wait_for_indexed_transaction` accepts on `item.tx_signature == signature` and
looks at nothing else.

**Input that exposes it.** An indexed record carrying the submitted signature
whose tags are not echoed back in the slots the client scans. Rust confirms it;
TypeScript spent the whole schedule and raised `CLIENT_INDEXER_TIMEOUT`. Which
slot carries a tag is the indexer's business, not a confirmation precondition.
The query is already by tag, so the re-check only restated the request.

**Evidence.**
`indexer-client.test.ts::"confirms the record Rust confirms, without re-checking
where the tags landed"`. Restoring the `tags.every(...)` predicate fails it.

**Note for the #158 merge.** `pr-158-impact.md` records that #158 moves Rust from
nothing to `transaction_matches_tags` using `.any(...)`. That is still weaker
than `.every(...)` and stronger than signature-only. Current Rust at HEAD is
signature-only and that is what the resolution order selects, so the port
matches HEAD. When #158 lands, tightening to `.any(...)` is a one-line change;
`.every(...)` should not come back.

### 3. Confirmation sent no page limit (`C21`)

`wait_for_indexed_transaction` passes `Some(50)`. TypeScript sent `undefined`,
leaving the page size to the server, so a busy tag could push the signature off
the page the client inspects.

**Evidence.** `indexer-client.test.ts::"asks for the same page size the Rust
confirmation asks for"` reads the request body. Fails without the change.

**Note for the #158 merge.** #158 deletes pagination from this path entirely, so
this line will be removed again. It is one line in `client.ts` and touches
nothing #158 conflicts with.

### 4. The client's indexer config never reached the indexer (`C21`, `C04`)

Rust holds `indexer_config: IndexerRpcConfig` and every delegating indexer method
passes `Some(config.unwrap_or(self.indexer_config))`. TypeScript had no such
field: confirmation polled a hard-coded `DEFAULT_INDEXER_POLL_CONFIG`, and
`getMerkleProofs`, `getNonInclusionProofs`, and `getInputMerkleProofs` forwarded
the caller's `undefined` to `ZolanaIndexer`, which then applied its own default.
A configured client behaved like an unconfigured one on both paths.

**Input that exposes it.** A client built with `waitForIndexer: true` and a
one-retry schedule, against an indexer reporting `block_time: 0`. Rust would
fail not-caught-up after two attempts; TypeScript returned the proof.

**Evidence.** Two tests, each failing without the change:
`indexer-client.test.ts::"honors the configured poll schedule rather than the
default"` and `::"substitutes its own indexer config when the caller omits one"`.
The client now takes `indexerConfig` and exposes it, mirroring
`with_indexer_config` / `with_indexer_poll_config`.

### 5. Six retryable error codes classified as fatal (`C01`, `C02`)

`retryCause` mapped four of the ten TypeScript codes that narrow Rust's
`ClientError::Rpc`. `ClientError::retry_cause` reports every `Rpc` as
`RetryErrorCause::Rpc`, so the six unmapped codes made a poll give up where the
Rust poll spends its schedule.

**Input that exposes it.** An indexer response with a `tx_viewing_pk` that is not
33 bytes. `indexer.rs::fixed_bytes` turns it into `ClientError::Rpc`;
`indexer.ts::decodeP256` raises `CLIENT_INVALID_RPC_RESPONSE`. This is the one of
the six with a live producer on both sides inside a polled closure.

**Evidence.** Paired tests.
Rust: `indexer.rs::a_malformed_viewing_key_classifies_as_the_rpc_cause` and
`::a_malformed_viewing_key_is_retried_for_the_whole_schedule` (three attempts,
`PollTimedOut { last_cause: Rpc }`).
TypeScript: `retry.test.ts::"spends the whole schedule on a malformed indexer
field, as the Rust poll does"` (three attempts, `CLIENT_POLL_TIMED_OUT` with the
rpc cause) plus the six new rows in the cause table. Removing the
`CLIENT_INVALID_RPC_RESPONSE` case makes both fail.

**Open question for Rust, not changed here.** Rust's own classification of a
malformed indexer body is inconsistent, and the port inherited the inconsistency
by matching it. A 31-byte `output_slot` hash is decoded by the API layer and
becomes `ClientError::Indexer { retryable: false }`, fatal on the first attempt
(`indexer.rs::rejects_malformed_output_slot_hash`). A 32-byte `tx_viewing_pk` is
length-checked in `indexer.rs` instead and becomes `ClientError::Rpc`, retried
for the whole schedule. Both are malformed bodies from the same response; one is
a transport hiccup and the other is not, purely by which layer happens to decode
the field. Retrying a body that will not parse differently is wasted schedule.
Making `fixed_bytes` and `decode_error` fatal would be the better fix, and would
let TypeScript drop `CLIENT_INVALID_RPC_RESPONSE` from the retryable set again.
Not done here: it is a Rust semantics change in the file #158 conflicts with, and
the resolution order says current Rust wins.

### 6. A dropped transaction was never resubmitted (`C05`)

`SolanaRpc::send_transaction` calls `send_and_confirm_transaction`, which keeps
resubmitting the transaction while it waits for confirmation. TypeScript
submitted once and only polled `getSignatureStatuses`, so a transaction the
leader drops timed out with `CLIENT_CONFIRMATION_TIMEOUT` where Rust confirms.

**Evidence.** `solana-rpc.test.ts::"resubmits a dropped transaction while
waiting, as send_and_confirm does"`: the first copy is never confirmed, the
resubmitted copy is, and the payload bytes are identical across all three sends
so the signature never changes.

## Divergences found and left in place, with reasons

### `confirmTransaction` searches transaction history (`C05`)

TypeScript sends `searchTransactionHistory: true`; Rust's
`RpcClient::confirm_transaction` does not, so it only consults the recent status
cache. TypeScript is the more permissive side: confirming a signature that has
aged out of the cache is a legal operation, and narrowing it would be exactly
the defect the brief describes. Left as a deliberate divergence. If they should
converge, Rust should adopt the search, not the reverse.

### `MERGE_INPUTS` is not exported (`C22`)

Rust exports `MERGE_INPUTS` from the transaction module; TypeScript keeps it
private. The fix belongs in `@zolana/transaction`, which this work does not own.
Recorded for that owner.

### `CLIENT_SOLANA_TRANSACTION_SIGNING` has no producer (`C02`)

The code exists but nothing raises it, because the wrapping would have to happen
around `signNativeTransaction` in `sdk-libs/ts/wallet/`, outside this scope. The
error test's `NO_TYPESCRIPT_PRODUCER` set conflates codes with no producer
anywhere against codes whose producer lives in another package; splitting it
would make the distinction visible. Not done.

## Evidence-backed parity, counted honestly

Of the six rows in this half, **none is fully `PARITY`**. What now holds is
narrower and worth stating as such.

**Ten behaviors carry a test that was run against the pre-fix code and failed.**
Account ordering in `compileLegacyTransaction`; confirmation accepting a
signature-only match; confirmation sending `limit: 50`; confirmation honoring the
configured schedule; the delegating indexer methods substituting the client's
config; the six-code retry classification; the TypeScript poll spending its
schedule on `CLIENT_INVALID_RPC_RESPONSE`; the two Rust-side classifications of a
malformed viewing key; and `sendTransaction` resubmitting.

**Two more are Rust-derived expectations rather than fix-discriminating tests.**
The `merge_transact` and `merge_zone` message assertions now read an oracle
`Message::new` produced, replacing hand-written account arrays. They demonstrate
that TypeScript agrees with Rust; they do not demonstrate a bug that was fixed.

The rows themselves stay open because each covers more surface than the
behaviors tested. `C21` alone spans the whole of `client.rs`, and closing it
means evidence for the validation orders, the error selections, and the
submission paths that were read but not tested.

Reading two files and finding them similar is what produced the audit's
thirty-five unsupported `PARITY` marks. These rows are not being marked.

## Verification

TypeScript, all green after the changes: `test:unit` (802 passed, 1 skipped),
`test:vectors`, `test:cross`, `typecheck`, `build`, `test:exports`.
Rust: `cargo test -p zolana-client --lib --features client`, 45 passed.

The two oracle tests double as staleness checks: they compare their committed
JSON against a fresh render and fail if the Rust side moves.
Regenerate with `ZOLANA_WRITE_ORACLES=1`.

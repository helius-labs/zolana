# Chunked spend uploads

The append protocol keeps its existing instruction encodings and behavior. New `CreateChunked`, `Grow` and `WriteChunk` variants follow the existing enum variants. They use the same owner-bound PDA and allocation helpers.

Chunked buffers use fixed 800-byte chunks, with an exact-length final chunk. The 24,000-byte payload limit needs at most 30 completion bits. Header byte45 selects the mode; bytes46..50 contain the bitmap while status is uploading. The loader validates the bitmap, written-byte total, size, status and reserved bytes. Preparation and commit require every chunk and the full allocated account length. Distinct chunks can arrive in any order; an identical retry is idempotent during upload, while conflicting bytes are rejected. Prepared and spent buffers reject writes and growth.

Preparation already loads a complete payload before verifying its proofs. Only then does `mark_prepared` set status1 and replace bytes46..80 with the freshness root. The loader interprets those bytes as freshness after preparation, preserving subsequent freshness refreshes. The completed written-byte count remains unchanged. This overlay adds no header or account size.

`SpendUpload::allocate_chunked` returns creation followed by the required growth instructions. Execute these in order before submitting chunks. Actual SBF execution confirmed that creation, both growth instructions and a final chunk for the full 24KB payload can share one transaction: Pinocchio limits each instruction's increase, not the combined increase across these top-level instructions. After allocation completes, `start_chunks` supplies full statement-prefix chunks, and `finish_chunks` supplies the boundary/proof chunks after validating the unchanged statement, payload variant and capacity suffix. The two sets are disjoint and their writes may overlap in flight. Existing `start`/`finish` and `upload_spend` retain append semantics.

The completion guarantee does not publish or prove a hash at allocation time. The owner authorizes each write, and the existing payment/certificate proof verification binds the fully assembled payload before any spend succeeds. Chunk uploads share one writable account, so chain execution remains serialized by account locking; the optimization removes per-chunk client confirmation dependencies.

Tests cover reverse order, exact ranges, duplicate/conflicting writes, full allocation, ownership, wrong modes, no-hole preparation and commit, transaction rollback, unchanged append tags and payloads, and the prepared metadata overlay. Sealed-account SBF mutation tests inject prepared/spent metadata rather than generating new proofs; the existing real-proof payment suite remains the source of proof/settlement validation.

Validation passed: five interface builder tests, two native buffer-loader tests, seven actual-SBF tests against the freshly rebuilt normal v1.54 program. The SBF suite took 0.20 seconds; that is correctness-test runtime, not upload latency. Logs are `target/chunked-buffer-interface.log`, `target/chunked-buffer-unit.log`, `target/chunked-buffer-sbf-build.log` and `target/chunked-buffer-sbf-tests.log`. Payment latency must be measured separately with the new concurrent harness.

The interface also appends the experimental `Payload::DagPayment` variant and `ADMITTED_DAG_PAYMENT_DOMAIN = 0x44535033` without changing existing variants. The shared uploader binds its variant and input-capacity suffix in the same way as the other committed-proof payloads. Program dispatch selects its fixed 512-input verifying key. The real-proof suite rejects attempts to submit the same proof under the ordinary admitted selector.
